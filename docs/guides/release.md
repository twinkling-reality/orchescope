# Release

How a maintainer turns this repository into the `orchescope` package on npm. Nothing here is automatic, and nothing in
this repository holds a registry credential.

## The publishable unit is `release/stage`

`apps/cli/package.json` is a workspace manifest. It depends on nine `workspace:*` packages that are compiled into the
bundle and never published, so `npm publish` from `apps/cli` would put dependency names on the registry that nobody can
install.

`pnpm package` stages the real thing in `release/stage`: the same manifest with the workspace ranges removed, the three
dependencies that stay external at runtime kept, development dependencies and scripts dropped, and `dist` plus the
licence and the readme beside it. That directory is what gets published, and the script refuses to produce it if a
workspace range survived staging, or if the declared binary is missing.

## Before publishing

```
pnpm verify                  # check, unit and integration, end to end
pnpm corpus:required         # archive acquisition and selected real-repository gate
pnpm corpus --exercise       # every pinned repository, including entries that measure runs
pnpm package                 # builds the bundle, stages, packs, installs and audits
```

`--exercise` is here rather than in `pnpm verify` because it installs an environment and runs third party
code, which is not something a routine gate should do. Leaving it out of both is how the two entries that
measure the declared against exercised join, which is the centre of this product, went unrecorded from
before 0.2.0 until after 0.5.0. `pnpm verify` covers the local subset through the corpus end-to-end test,
`pnpm corpus:required` proves the selected digest-pinned archive path, and `pnpm corpus` covers every entry
that needs no run. The exercise line adds the runtime populations nothing else looks at.

`pnpm package` writes `release/release-summary.json`. Read it rather than trusting the exit code:

| Field | What it has to say |
| --- | --- |
| `publishableUnit` | `release/stage` |
| `workspaceDependencies` | empty |
| `missingRequiredFiles` | empty |
| `installSmokeTest.ok` | `true`, with a detail naming the components it discovered |
| `publishedVersion` | the version being released |

The smoke test installs the tarball into a temporary prefix and audits a small TypeScript and Python project with it.
That is the check that matters, because the parsers resolve a native binding and a WebAssembly grammar relative to their
own package directories, and only a real audit proves those resolve from an installed tree.

Continuous integration runs the same `pnpm package` on every push and uploads the tarball, its checksum and the summary
as the `release-candidate` artifact. A release should come from a green run of that job.

## Version

The version lives in two places, and a test fails when they disagree:

- `apps/cli/package.json`, which is what the registry serves
- `ORCHESCOPE_VERSION` in `apps/cli/src/context.ts`, which is what `--version`, every JSON document and every stored
  scan record

Bump both, then run `pnpm test` before packaging.

## Publishing

```
cd release/stage
npm publish
```

`publishConfig` in the manifest asks for public access and for provenance. Provenance is generated by the registry from
a workflow identity, so it works from a GitHub Actions job with `id-token: write` and fails from a laptop. Publishing by
hand therefore means one of two things, and both are honest choices as long as the release notes say which:

- publish from a workflow that has `id-token: write` and a registry credential the maintainer supplies, and the release
  carries an attestation
- publish locally with `npm publish --no-provenance`, and the release carries no attestation

There is no release workflow in this repository, because adding one would mean claiming a secret exists that does not.

## After publishing

```
npx orchescope@<version> --version
npm install -g orchescope
orchescope doctor
```

Check that the registry has what this source builds, and record the answer in the changelog rather than asserting it:

```
npm pack orchescope@<version>
shasum -a 256 orchescope-<version>.tgz          # against the sha256 pnpm package printed
```

Then create the GitHub release, because the README tells a stranger it exists:

```
gh release create v<version> \
  release/orchescope-<version>.tgz \
  release/orchescope-<version>.tgz.sha256 \
  --title "orchescope <version>" --notes-file <the changelog section>
```

The install section says "the same archive is attached to every release with its sha256 beside it", and a reader who
follows that to an empty releases page has been told something untrue by the front page of the project. This step is
here because it was not, and it lapsed for two versions without anything noticing.

Then read the install section of the README as a stranger would and correct anything the publish has just made untrue.
`release/release-summary.json` records `published: false` because the script that wrote it published nothing; it is not a
claim about the registry.

Expect a two factor prompt. An account with it enabled answers `npm publish` with `EOTP` and a browser link, so the
publish is a person at a keyboard rather than something a script or an agent can finish. Nothing partial is written when
it stops there. Expect also a warning that `bin[orchescope]` was invalid and removed: npm normalises `./dist/orchescope.mjs`
to `dist/orchescope.mjs` and assigns it straight back, so the binary survives and the warning is noise.

## The notes

[CHANGELOG.md](../../CHANGELOG.md) carries a section per released version, written by hand. A GitHub release body is
that section pasted in. Two things belong in every section and are easy to leave out: whether the version carries a
registry attestation, and any change that will move a reader's finding counts or refuse a configuration they already
have.

## What is not automated

- No tag or GitHub release is created by a script here, and the changelog is written rather than generated.
- No credential, token or OIDC configuration is stored in this repository.
- Nothing deprecates or unpublishes a version.
