# Release

How a maintainer turns this repository into the `orchescope` package on npm. Nothing here is automatic, and nothing in
this repository holds a registry credential.

## The publishable unit is `release/stage`

`apps/cli/package.json` is a workspace manifest. It depends on ten `workspace:*` packages that are compiled into the
bundle and never published, so `npm publish` from `apps/cli` would put dependency names on the registry that nobody can
install.

`pnpm package` stages the real thing in `release/stage`: the same manifest with the workspace ranges removed, the three
dependencies that stay external at runtime kept, development dependencies and scripts dropped, and `dist` plus the
licence and the readme beside it. That directory is what gets published, and the script refuses to produce it if a
workspace range survived staging, or if the declared binary is missing.

## Before publishing

```
pnpm verify                  # check, unit and integration, end to end
pnpm package                 # builds the bundle, stages, packs, installs and audits
```

`pnpm package` writes `release/release-summary.json`. Read it rather than trusting the exit code:

| Field | What it has to say |
| --- | --- |
| `publishableUnit` | `release/stage` |
| `workspaceDependencies` | empty |
| `missingRequiredFiles` | empty |
| `installSmokeTest.ok` | `true`, with a detail naming the components it discovered |
| `publishedVersion` | the version being released |

The smoke test installs the tarball into a temporary prefix and audits a small TypeScript and Python project with it.
That is the check that matters, because the parsers resolve a native binding and a WebAssembly grammar relative to their
own package directories, and only a real audit proves those resolve from an installed tree.

Continuous integration runs the same `pnpm package` on every push and uploads the tarball, its checksum and the summary
as the `release-candidate` artifact. A release should come from a green run of that job.

## Version

The version lives in two places, and a test fails when they disagree:

- `apps/cli/package.json`, which is what the registry serves
- `ORCHESCOPE_VERSION` in `apps/cli/src/context.ts`, which is what `--version`, every JSON document and every stored
  scan record

Bump both, then run `pnpm test` before packaging.

## Publishing

```
cd release/stage
npm publish
```

`publishConfig` in the manifest asks for public access and for provenance. Provenance is generated by the registry from
a workflow identity, so it works from a GitHub Actions job with `id-token: write` and fails from a laptop. Publishing by
hand therefore means one of two things, and both are honest choices as long as the release notes say which:

- publish from a workflow that has `id-token: write` and a registry credential the maintainer supplies, and the release
  carries an attestation
- publish locally with `npm publish --no-provenance`, and the release carries no attestation

There is no release workflow in this repository, because adding one would mean claiming a secret exists that does not.

## After publishing

```
npx orchescope@<version> --version
npm install -g orchescope
orchescope doctor
```

Then update the install section of the README: it currently says the package is not published, and that sentence is only
true until it is. `release/release-summary.json` records `published: false` because the script that wrote it published
nothing; it is not a claim about the registry.

## What is not automated

- No tag, changelog or GitHub release is created by a script here.
- No credential, token or OIDC configuration is stored in this repository.
- Nothing deprecates or unpublishes a version.
