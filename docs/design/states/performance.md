## What a designer needs to know beyond the list

WHAT THE DEMONSTRATION CANNOT SHOW. `demonstration-system` (the audit of apps/demo with no runs) reaches exactly four Performance states: the measurements refusal, no overlay block at all, the runs refusal, and the benchmark refusal whose command names a real scenario. It is the only bundle reaching that last one, because it is the only bundle with scenarios defined and no benchmark. `demo-populated` (the same project after the tour plus test, benchmark, chaos, compare and goal) is the only bundle reaching the populated benchmark, the scenario run kind, task success succeeded, the ten run ceiling and the withheld summary block.

WHAT NO CACHED BUNDLE REACHES AT ALL, ranked by how much design depends on it:
1. Anything involving cost. No price is configured anywhere in this repository (grep for inputPerMillion finds only the schema), and cost is only ever attached when the project config carries a price for the observed provider/model. So: the cost overlay block never renders in any report produced without a configured price table, every cost cell in both tables reads not measured, the cost distribution row never appears, and the cost sort ordering (unpriced rows at negative infinity) has never been seen. Four states, one cause.
2. Failure. Every cached run is completed and every cached variant is 3 of 3. Failed, timeout, cancelled and budget exceeded statuses, task success failed, and a variant reporting failedRuns are all unreached, and the runs table renders no reason for any of them: RunRecord.failureReason and RunRecord.exitCode exist and no cell shows either.
3. Scale. The largest measured system has 15 rows. Neither the measurements table nor the runs table nor the benchmark tables are windowed at any size, and only the overlay bars are, above 200 rows. A trace over pydantic-ai (1953 components) would put the first unwindowed thousand row table on the screen.
4. Sample sizes other than three. Every quantile branch except three withheld is unreached, including the one where the withheld block disappears entirely at 100 samples.
5. The benchmark variants that are not three: one variant (which also shortens the limitations list from five entries to three), and one repetition (which prints "1 repetitions").

STATES THAT ARE STRUCTURALLY UNREACHABLE, not merely unfixtured. Worth knowing before designing them: the overlay carries no values refusal (documented in report-system.md as one of the four Performance empty states, but the latency overlay only exists when there are measurements and the cost overlay only when there are costs, so neither can be present and empty); an overlay with no caveat or no unit on this screen (both kinds always carry both); a benchmark with no limitations (the one machine note is always appended); a distribution with sampleSize 0; the withheld summary block with an empty list (all five listed distributions share a sample size); a run with status running or kind benchmark_variant, chaos or demonstration (three of the five kinds and one of the six statuses are schema only, because benchmark and chaos both record their runs as kind scenario).

TWO DEFECTS THAT ARE THEMSELVES STATES. DistributionRow renders min, all four quantiles and max with formatDuration whatever the measurement is, so in demo-populated today the Total tokens row reads min 801 ms and max 1.56 s, and Model calls p50 reads 3 ms. And the variant sentence concatenates counts without selecting a plural, so a single repetition benchmark reads "1 repetitions, 1 completed, 0 failed". Both are visible in a designed mock and both need a decision rather than a silent fix.

TWO SILENCES. The runs table is capped at ten by the audit default and says nothing about it, and in demo-populated the nine runs behind the benchmark are among those dropped, so the benchmark reports variants whose runs are not in the table above it. And the measurements table is the only numeric block on the screen with no basis chip, while the bars beside it carry one.

ROW COUNT VERSUS ENTRY COUNT. bundle.componentMetrics carries one entry per component per run (150 in demo-populated); graph-index merges them by component before the table sees them (15 rows), summing counters, summing cost and taking the maximum p95. A designer sizing this table from the bundle field will be out by an order of magnitude.
