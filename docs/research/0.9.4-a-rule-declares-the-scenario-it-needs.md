# A rule declares the scenario it needs, and the product composes it

A design, written before any code, for the four items
[the closing-the-loop design](0.9.4-closing-the-loop-design.md) left standing in item 3: the predicate
becoming data, the finding carrying its requirement when unmet, the composition half of `init --scenario`,
and a template that does not offer a command its own evaluator cannot pass.

Every number below was produced by running this build against the pinned corpus or against a copy of a
system it audits. Each claim carries the command behind it or its `file:line`. Nothing from
[the closing-the-loop design](0.9.4-closing-the-loop-design.md),
[the goal selection design](0.9.4-which-runs-a-goal-is-judged-against.md) or
[ADR 0017](../architecture/adr/0017-a-goal-is-judged-against-the-same-work-twice.md) is re-derived here.

**What was built, and where it differs from this design.**
[ADR 0018](../architecture/adr/0018-a-rule-declares-the-scenario-it-needs.md) records the decision as it
shipped, and every item below is as designed. Three things are worth stating because they were decided
under contact with the code rather than in advance.

The enumerating check landed with the composer rather than with the declaration, because what it enumerates
is "a rule that declares a requirement has a repository where the product can satisfy it", and until the
composer existed the second half of that sentence had nothing to check. Splitting it would have meant a
test-local second composer, which is the drift the single definition exists to prevent.

`@orchescope/workspace` gained a development dependency on `@orchescope/scenarios`, which this design did
not anticipate. The round trip that matters is compose, parse with the real parser, match with the real
matcher, and those three live in three packages; a test that reimplemented any of them would prove nothing
about the pair that can actually drift.

And the composed prohibited effect is written with `maxCount: 0` under a kind this build names in two
places in one file, rather than resolved from recorded effects. Nothing in a static audit records an effect
kind, so resolution had no input, and the alternative considered, the kind this product's own shim emits
for a plain outbound write, would have required either a copied literal or a new dependency edge into the
96 KiB shim bundle.

## The short version

| the brief | what the code and the corpus say it is |
| --- | --- |
| three rules compute the same predicate inline | **two of them compute two different predicates.** `prompt-injection-boundary` accepts `*`, the component identifier and both names; `retry-around-non-idempotent-operation` accepts neither `*` nor the identifier. One definition cannot say both, so making it data is also a decision about which of the two is right. |
| the third rule computes it inline too | **`duplicate-side-effect` asks a different kind of question.** Its predicate is not about what a scenario declares; it is about which scenario a recorded run belonged to. That clause is not composable and the file has to say so rather than pretend. |
| "either the evaluator changes with the candidate, or the candidate is offered with the reason" | **the first option does not exist.** A target that does not exit is recorded `timeout` (`packages/scenarios/src/repetition.ts:182-192`) and a repetition that is not `completed` fails whatever its evaluators say (`packages/scenarios/src/run.ts:225-231`). No evaluator rescues a non-terminating command, so only the second option is real, and the reason it gives is stronger than the one the brief supposes. |
| "a four line unrunnable YAML moves the same number a real scenario would" | **true of that number and of nothing after it.** Run end to end below: the goal it yields carries one criterion, a static rescan, prescribes no rerun, and states `comparisonUnavailable`. ADR 0017 already contains the trap; composition does not widen it. |

## What the tracing corrected

### 1. The two static rules do not compute the same predicate

`prompt-injection-boundary` (`packages/findings/src/rules/static-policy.ts:1006-1022`) accepts a fault
whose target is `*` or an exact member of `{source.id, source.identity.localName, source.displayName}`.
`retry-around-non-idempotent-operation` (`:162-175`) accepts only
`{target.identity.localName, target.displayName}`: not `*`, not the component identifier.

So a scenario declaring `target: '*'`, which is the schema's own way of saying "every match"
(`packages/schema/src/chaos.ts`, `FaultSpec.target`), satisfies one rule and not the other, and a scenario
naming `tool:issue_refund` satisfies one and not the other. Neither difference is argued anywhere. Making
the predicate data forces the choice, and the choice is the wider of the two: **`*` and the identifier are
accepted for every requirement**, because a fault aimed at everything is aimed at this component too, and
an identifier is the spelling the audit's own JSON hands an operator.

This widens `retry-around-non-idempotent-operation`. Measured cost: none. No pinned checkout carries a
scenario at all, and the demonstration system's two candidate scenarios already name `issue_refund`, which
is `identity.localName`, so they matched before and match after.

### 2. `duplicate-side-effect` asks about recorded work, not about a declaration

`packages/findings/src/rules/reconciliation.ts:335-341` collects the scenario identifiers of the runs that
recorded the duplicate and takes the first stored scenario among them. There is no fault clause, no
evaluator clause and no expectation clause. **Nothing an operator can write into a file satisfies it**;
only running a scenario that reproduces the duplicate does.

That is not a defect to fix here, and narrowing it by bolting a `no_duplicate_effects` clause onto it
would change a shipped answer for no evidence. It is a second kind of clause, and the honest treatment is
to carry it as one: a requirement may say "a scenario whose recorded runs produced this", the composer
cannot declare that clause into a file, and the file says which finding is waiting on a run rather than on
an edit.

### 3. No evaluator saves a command that does not exit

The brief offers two remedies for a candidate that is a long running server. The first does not exist.

`repetitionStatus` (`packages/scenarios/src/repetition.ts:182-192`) returns `timeout` when the supervisor
timed the target out, and `failed` when it exited non zero. `everyRepetitionPassed`
(`packages/scenarios/src/run.ts:225-231`) requires `status === 'completed'` **before** it looks at a single
evaluator. So a server that never exits fails at `target.timeoutMs` with every evaluator the scenario could
possibly declare, and the choice of evaluator is not what is wrong.

Two consequences.

- **The template's `exit_code: equals 0` evaluator decides nothing.** `repetitionStatus` already returns
  `failed` for any non zero exit, so the evaluator can only ever agree with the status that already
  decided. It stays, because a scenario with no evaluator at all passes vacuously
  (`[].every(...)` is true), and a template that ships a scenario deciding nothing is worse than one
  shipping a redundant check. What changes is that it is no longer the only thing the template emits.
- **The reason offered beside a candidate is about the target, not about the evaluator.** "This evaluator
  cannot pass" would be a false explanation of a true refusal.

Nothing this build reads says which of a repository's declared commands exits on its own. `npm run start`
is a server in one repository and a batch job in the next, and the only way to tell is to run it, which is
the one thing `startCommandCandidates` exists not to do
(`packages/workspace/src/start-command-candidates.ts:6-20`). So the template states the property that
decides, states what happens to a command that lacks it, and does not guess which candidate is which.
Guessing is what a name list would be.

### 4. The unrunnable scenario buys eligibility and nothing after it

Run end to end on a copy of the demonstration system, with a four line scenario satisfying
`retry-around-non-idempotent-operation`'s predicate and `target.command` set to
`['definitely-not-a-real-binary-xyz','--nope']`, plus one real traced run so the runtime evidence guard is
cleared:

    orchescope audit          -> retry-around-non-idempotent-operation eligible = true,
                                 "Repository scenario unrunnable faults this operation and
                                  checks for duplicate effects."
    orchescope goal create    -> one acceptance criterion, AC-01 finding_resolved
                                 validation.scenarioIds       []
                                 validation.baselineRunIds    []
                                 validation.requiresExecution false
                                 comparisonUnavailable        "the runs that exercised these components
                                                               belong to no scenario, so this plan has no
                                                               way to record a run made after the change"

And without a run at all, on a copy of `openai-cs-agents-demo` carrying the same four line file,
`goal create` refuses outright: "Finding OSC-JVTOX-2656 needs runtime evidence before it can be verified,
and no baseline run was supplied."

**So the trap is already contained, one layer down, by a rule this repository decided on evidence.**
Eligibility is a claim that a bounded change exists and that a check exists which could decide it. What a
goal is *judged against* is chosen from recorded execution (ADR 0017), and an unrunnable scenario has no
recorded execution, so it names no validation scenario, prescribes no rerun, banks no metric criterion, and
the goal document says which question failed.

Composition does not widen that. It narrows it in one direction and in one only: the file it writes is
built from candidates the repository itself declared, so the operator filling `target.command` is choosing
from their own manifest rather than inventing a string.

**What is deliberately not done about it.** The finding could say whether the scenario it matched has ever
run. It will not, because the only run population a rule may read is the window the audit reconciled
(`packages/findings/src/rule.ts:126-135`), and "no run belongs to it" derived from a bounded window is a
claim about the window presented as a claim about the repository. That is the shape of confident wrongness
this product exists to remove, and the containment above needs no help from it.

## The design

> **A rule that gates eligibility on a scenario declares the scenario it needs as data, beside its
> remediations. One definition is used to search for a scenario and to say what is missing. The finding
> carries that requirement when it is unmet. `orchescope init --scenario` composes a scenario from the
> requirements the audit's own findings carry, with the fields only the operator knows left blank and the
> repository's own candidates beside them.**

### D1. The requirement, as one document

A new schema module, `packages/schema/src/scenario-requirement.ts`:

    ScenarioRequirement {
      faultKinds: FaultKind[]          // any one of these, aimed at one of faultTargets, satisfies the clause
      faultTargets: string[]           // spellings resolved from the graph, the writable one first
      evaluatorKinds: EvaluatorKind[]  // all of these must be declared
      prohibitedEffects: boolean       // expect.prohibitedEffects must name at least one effect
      recordedScenarioIds?: string[]   // only a scenario among these can satisfy it, when the rule asks about
                                       // recorded work rather than about a declaration
    }

`EvaluatorKind` is derived from the evaluator union rather than written out a second time:
`Evaluator.anyOf.map((option) => option.properties.kind.const)` returns the nine kinds
(`packages/schema/src/evaluator.ts:23-93`), so a kind added to the union is a kind this vocabulary knows
without anybody remembering to add it.

`Finding` gains `scenarioRequirement` as an optional field. Optional additions need no version bump and no
migration, which is the reasoning [ADR 0016](../architecture/adr/0016-two-proofs-of-a-source-location.md)
applied to the content proof and [ADR 0017](../architecture/adr/0017-a-goal-is-judged-against-the-same-work-twice.md)
applied to `ComparisonSide` and `ValidationPlan`.

### D2. One matcher, in `@orchescope/domain`

`packages/domain/src/scenario-requirement.ts` exports the search and the sentence:

    scenarioSatisfying(requirement, scenarios): Scenario | undefined
    describeScenarioRequirement(requirement): string
    bindScenarioRequirement(declared, { faultTargets, recordedScenarioIds }): ScenarioRequirement

Domain rather than findings, because `@orchescope/workspace` composes the file and `@orchescope/findings`
searches for one, and the two must not be able to disagree about what satisfies a requirement. Workspace
already depends on domain and cannot depend on findings without pointing an assembly package at a core one
it has no other use for. This is the same reasoning that moved `MINIMUM_SAMPLES_PER_SIDE` and
`metricDecidedByPresence` into domain: two independent copies of one rule are two answers.

`bindScenarioRequirement` is what keeps the declaration and the instance from drifting. A rule declares the
constant clauses on itself; at evaluation it binds only the resolved parts, so the kinds a finding names
are always the kinds the rule declared.

### D3. What each rule declares

    prompt-injection-boundary
      faultKinds        [prompt_injection_in_content]
      evaluatorKinds    [no_duplicate_effects]
      prohibitedEffects true
      faultTargets      bound to the untrusted sources the finding names

    retry-around-non-idempotent-operation
      faultKinds        [tool_timeout, side_effect_partial_success]
      evaluatorKinds    [no_duplicate_effects]
      prohibitedEffects false
      faultTargets      bound to the retried operation

    duplicate-side-effect
      faultKinds        []
      evaluatorKinds    []
      prohibitedEffects false
      recordedScenarioIds bound to the scenarios of the runs that recorded the duplicate

**One narrowing, stated.** `prompt-injection-boundary` searches today against every untrusted source in the
graph while its finding names at most five (`static-policy.ts:1050`). The requirement carries the sources
the finding names, so the finding's own statement is what decides it, and a reader can check the decision
against the document rather than against a set the document does not contain. Measured cost: none, because
no pinned checkout carries a scenario and the demonstration system does not fire this rule. A scenario that
faults a sixth source and no other still satisfies the requirement by aiming at `*`.

### D4. The finding carries the requirement when it is unmet

`Finding.scenarioRequirement` is present exactly when the rule wanted a scenario and found none. That makes
one invariant a check can assert: **the requirement is present if and only if the finding is ineligible for
want of a scenario.** When a scenario matches, the finding names it in `goalReason` and prints it in
`suggestedExperiment`, which is what it does today.

`goalReason` is composed from the requirement rather than written out per rule, so the sentence names the
fault kind, the target, the evaluator kinds and the expectation an operator has to write, in the schema's
own vocabulary. Three separate prose strings that could each drift from the predicate beside them become
one sentence generated from the predicate.

**`suggestedExperiment` stops being dropped.** Today an unmet predicate removes it entirely, which withdraws
the specification in exactly the case a reader needs it. On the unmet branch it names the command that
writes the scenario, `orchescope init --scenario`, and keeps the same `expectedSignal` the met branch
carries, because the signal the experiment is looking for does not depend on whether the file exists yet.

### D5. `init --scenario` composes

`initCommand` already holds the store (`apps/cli/src/commands/workspace-commands.ts:22`). It reads
`latestReport`, collects the distinct `scenarioRequirement` of the findings in it, and passes them to
`initWorkspace` as an option, so `@orchescope/workspace` composes from a list of requirements and never
learns what a store is.

The composed file is one scenario, not one per finding, because `init --scenario` writes one file and
because a scenario carrying several faults is this product's own idiom: `orchescope chaos` supplies one
plan per fault so an outcome is attributable to a single fault
(`packages/usecases/src/scenario.ts:141-155`), while `orchescope test` runs the scenario as written. The
file says which of the two it is asking for.

What composition writes, per requirement, with no branch on any rule identifier:

- **faults**: one fault, first declared kind, aimed at `faultTargets[0]`, delivered cooperatively, with the
  other resolved spellings listed beside it as comments.
- **evaluators**: each required evaluator kind, added to the `exit_code` evaluator the template already
  writes.
- **expect.prohibitedEffects**: one entry, `maxCount: 0`, whose `kind` is a token this composer writes and
  writes again into the injection payload, so the instruction the fault injects asks for exactly the effect
  the expectation forbids. It is not read from any repository and it names no framework: it is one string
  appearing twice in one file, and the file says what makes it decide and what leaves it undecided.
- **a requirement with no declarable clause** is listed by finding identifier with the reason, which for
  `duplicate-side-effect` is that only a recorded run satisfies it.

A requirement whose clauses are all empty contributes nothing to the YAML and one line to the comment
block. There is no `if` on a rule identifier anywhere in the composer; if one is ever needed, the
declaration in D1 is not carrying enough and the declaration is what changes.

### D6. The template says what decides a candidate

Above the candidate list, in the `target` block, one sentence about the property that decides and one about
the consequence, both of them facts about this build rather than advice:

    # A target Orchescope runs has to exit on its own. One that does not is stopped at target.timeoutMs
    # and recorded `timeout`, and a repetition that did not complete fails whatever its evaluators say.
    # Nothing here can tell which of these does that, so none of them is picked for you.

That is the whole of the second option the brief offers, and by the trace in item 3 above it is the only
one that exists.

### D7. The check that enumerates

`tests/e2e/scenario-requirement-rules.test.ts`, built the way `tests/e2e/goal-eligible-rules.test.ts`
enumerates remediations: one case per rule that declares a `scenarioRequirement`, and a rule declaring one
with no case is a failing check rather than a quiet one.

Each case is a pair, through the real command line:

1. a repository that fires the rule with no scenario. The finding must be ineligible **and** must carry a
   requirement naming what is missing.
2. the same repository with that requirement satisfied, and the finding goal eligible. For the two static
   rules the second half is `orchescope init --scenario`, filling in `target.command`, moving the file to
   `scenarios/` and rescanning. For `duplicate-side-effect` it is a recorded run, because that is what its
   requirement says and a case that satisfied it any other way would be proving something the rule does not
   ask.

### D8. What the corpus is asked

The sweep in the baseline is re-run after the change and the two numbers stated: how many of the 12 gated
findings carry a requirement, and how many carry a suggested experiment. Both are expected to move from 0
to 12. **No eligibility is expected to move**, because nothing here writes a scenario into a pinned
checkout, and if any of the 19 eligible findings moves, that is a defect in this design.

`pnpm corpus` itself is expected to be unmoved: nothing here touches a discovery reader, an adapter, a
matcher or a rule's firing condition. The 48 matched expectations, the 1588 semantic assertions, the 88
injected shapes and the 87 recognition names should all stand.

## Falsifiers

Each is run against the tree at `3d8bd08` and shown failing, then against the new tree and shown passing.
Anything that passes both ways is labelled a guard and is not counted as a falsifier.

- **F1, the requirement is carried.** A repository that fires `prompt-injection-boundary` with no scenario
  produces a finding whose `scenarioRequirement` names the fault kind, a resolved target, the evaluator
  kind and the prohibited effect clause. **Old tree: the field does not exist**, so the assertion fails on
  the document rather than on an import.
- **F2, the specification survives the case that needs it.** The same finding carries a
  `suggestedExperiment`. **Old tree: dropped.**
- **F3, one definition.** A scenario built from a finding's own requirement, and nothing else, satisfies the
  rule that produced it. **Old tree: nothing to build from.**
- **F4, composition.** On a copy of a real repository: audit, `init --scenario`, fill in only
  `target.command`, move the file, rescan, and the finding is goal eligible. **Old tree: the static
  template satisfies no predicate**, which is the measurement in the closing-the-loop design.
- **F5, the terminating condition is stated.** The template that offers a candidate states what happens to
  a target that does not exit. **Old tree: it does not.** A pin on a document, and it is labelled as one.
- **F6, the statement is true.** A scenario whose target does not exit is recorded `timeout` and does not
  pass, with `no_duplicate_effects` declared, which would pass on its own. A **guard**: it holds on both
  trees, and it is what makes F5 more than a sentence.
- **F7, the widening does not narrow.** The demonstration system's `retry-around-non-idempotent-operation`
  still matches `support-desk-duplicate`. A **guard**.
- **F8, `duplicate-side-effect` is not composable and says so.** Its requirement carries
  `recordedScenarioIds` and no declarable clause, and the composed file names the finding as waiting on a
  run. **Old tree: no requirement at all.**

## Sequencing, as separable commits, each with its own gate

    1. Declare the scenario a rule needs where the rule declares its remediations.     F1, F2, F3, F7, F8
    2. Say what decides a command the template offers.                                 F5, F6
    3. Compose the scenario an audit's own findings ask for.                           F4

Commit 1 carries the schema change, the matcher, the three rules and the enumerating check together,

## What this design does not fix

- **A grouped finding states the requirement of its first instance.** `merge`
  (`packages/findings/src/grouping.ts:97-134`) spreads the representative draft, which is already how
  `goalEligible`, `goalReason` and `suggestedExperiment` behave. A repository with two retried operations
  and a scenario for the second is told about the first. Existing behaviour, made visible rather than
  introduced, and changing it means deciding what a requirement over a group means.
- **`saveScenario` does not move a scenario between projects**, recorded above with the reason it is not a
  one line fix.
- **A composed fault reaches only a cooperative target.** The plan is handed over as `TARGET_ENV.faultPlan`
  (`packages/runtime/src/session.ts:183-185`) and `startFaultProxy` has no non test caller, so the composed
  `faults` block is something only a target that implements the protocol honours. The file says so; the
  runner is not changed.
- **`expect.prohibitedEffects` on a target that reports no effect vocabulary passes vacuously.** That is
  the shipped semantics of an expectation nothing matched, and the composed file states what would make it
  decide.
- **The corpus cannot fire `duplicate-side-effect`**, so the third rule's conversion is measured on the
  demonstration system alone.
- **`orchescope init --scenario` is a command line surface.** MCP exposes no `init` tool
  (`packages/mcp/src/tools.ts`), so an agent gets the requirement on the finding and writes the file
  itself. Adding a tool is a separate decision about what an agent may write into a repository.
