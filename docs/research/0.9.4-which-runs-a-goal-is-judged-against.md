# Which runs a goal is judged against

A design, written before any code, for the one defect
[the closing-the-loop design](0.9.4-closing-the-loop-design.md) left standing in the improvement loop: a
goal's baseline and a goal's validation scenarios are chosen by two unrelated heuristics, and nothing
checks that the two sides of the resulting comparison describe the same work.

Every number below was produced by running this product against a system it audits, or by running the real
command line over the pinned corpus. Each carries the command behind it or its `file:line`. Nothing from
[the closing-the-loop design](0.9.4-closing-the-loop-design.md) or
[ADR 0016](../architecture/adr/0016-two-proofs-of-a-source-location.md) is re-derived here.

**What was built, and where it differs from this design.** One thing changed under contact with the code,
and it is recorded here rather than quietly absorbed.

**The sample floor is a property of the criterion, not of the comparison.** This document said reachability
required the floor, and building it that way withdrew the one criterion the improvement loop actually
closes on. `duplicateSideEffects` is decided by presence rather than by distribution
(`packages/comparison/src/compare.ts`, `metricDecidedByPresence`): an effect that happened once and now
happens never is a categorical change, and `compareMetric` decides it at any sample count. The
demonstration system's `support-desk-duplicate` declares one repetition, and gating every metric criterion
on three samples made `tests/e2e/improvement-loop.test.ts` fail on the goal it is written to prove. So
reachability now asks whether the two sides describe the same work, and the floor is asked separately, of
the criteria that are claims about a distribution: `metric_improvement`, and `metric_not_worse` on
`successRate`. That is the same principle the plan already followed, applied one level finer: state no
criterion whose deciding command cannot decide it, and no criterion is more decidable than the metric it
names. Everything else below is as designed.

## The defect, run end to end on the shipped tree

Not argued. Executed, at `7678100`, against a clean copy of `apps/demo`, following the plan the product
itself printed, verbatim and in order.

    orchescope audit --json
    orchescope test --scenario support-desk --repetitions 3
    orchescope test --scenario support-desk-duplicate --repetitions 3
    orchescope test --scenario support-desk-faults --repetitions 3
    orchescope compare run_c6adb0cba9092c2c latest --goal OSC-GOAL-0001
    orchescope goal validate OSC-GOAL-0001

That plan is `OSC-GOAL-0001`, cut from `independent-calls-run-sequentially`. The comparison it prescribes
resolves to:

    baseline  (support-desk repetition 3, 3 repetitions)         no fault plan
    candidate (support-desk-faults repetition 3, 3 repetitions)  fault plan fp_5cab10f8c615cb56

**Two different scenarios, one of them under an injected fault plan**, compared as though they were the
same work. The verdict is `regressed`, "task success declined, so no latency or cost improvement makes
this an improvement". Its deltas:

    durationMs             201.67 -> 249    regressed    3/3
    successRate                 1 -> 0      regressed    3/3
    totalTokens              1395 -> 394    improved     3/3
    modelCalls                  4 -> 2      improved     3/3
    toolCalls                   6 -> 2      improved     3/3
    retries                     0 -> 1      regressed    3/3
    errors                      0 -> 3      regressed    3/3
    duplicateSideEffects        0 -> 0      unchanged    3/3
    userInterventions           0 -> 0      unchanged    3/3
    durationMs.p95            222 -> 274    regressed    3/3

Every one of those ten lines is about the difference between two scenarios. `successRate 1 -> 0` is the
faults the second scenario exists to inject. `totalTokens 1395 -> 394 improved` is a different task doing
less work, reported as a win. The comparison document says none of this: `limitations` records the sample
size and the missing graph delta, and nothing anywhere states that the two sides ran different scenarios
under different conditions.

An operator who changed nothing at all and ran this plan is told their goal regressed.

This is not the sample-floor problem, which is fixed: both sides carry three samples, and
`durationMs.p95` is decided rather than withheld. The floor is reachable. What is wrong is **which runs
are on each side**.

### Why it happens, at two lines

`packages/usecases/src/goal.ts:91-94,103` takes the twenty newest completed runs in the project, keeps the
completed ones and slices three off the front. Nothing relates them to the scenarios the plan will rerun.

`packages/usecases/src/goal.ts:45-62` picks the scenarios by matching a scenario's tags against the
finding's tags and components, and falls back to `chosen = matches.length > 0 ? matches : scenarios` when
nothing matches, that is to **every scenario in the project**, sliced to three.

Measured on the demonstration system, three goals cut from three findings with entirely different tags
(`latency, parallelism`; `timeout`; `approval, side-effect`) received the identical selection:

    OSC-QRMNF-2290 independent-calls-run-sequentially  -> ["support-desk","support-desk-duplicate","support-desk-faults"]
    OSC-MIQMZ-5859 model-call-without-timeout          -> ["support-desk","support-desk-duplicate","support-desk-faults"]
    OSC-MNXUF-3353 side-effect-approval-boundary       -> ["support-desk","support-desk-duplicate","support-desk-faults"]

with the same three baseline runs each time. The tag rule matched nothing in any of the three cases and
the fallback returned everything, so on the only system in this repository that has scenarios at all, the
matching contributes exactly nothing and the fallback does all the work.

## What the name matching costs, measured over all 56 pinned repositories

The rule at `goal.ts:51-59` is kept verbatim and evaluated against the corpus vocabulary, gathered by
running `orchescope audit --json` over every cached checkout. **56 repositories, 101 findings, 20 of them
goal-eligible, naming 371 distinct component identifiers, carrying 10 distinct finding tags in total**
(`approval, complexity, coverage, cycle, idempotency, positive, prompt-injection, retry, side-effect,
timeout`).

The measurement gives the rule the most favourable input it can have: a scenario tagged with the **exact
name of a component the finding is about**. If substring matching discriminates anywhere, it discriminates
here.

**Within one repository**, which is the real scope because a project holds one repository:

    intended matches      642
    unintended matches    165        20.4 per cent of all matches are wrong
    repositories where at least one match is wrong    15 of 50 with findings

    openai-agents-js                     4 findings   52 intended   43 unintended
    openai-agents-js-exercised           4 findings   52 intended   43 unintended
    openai-agents-js-provider-exercised  4 findings   52 intended   43 unintended
    openai-agents-python                 4 findings   56 intended    6 unintended
    agentic-browser                      3 findings   11 intended    6 unintended

Across the whole corpus vocabulary, which is what a rule has to survive as an agent system grows:

    intended matches      642
    unintended matches   1123        63.6 per cent of all matches are wrong
    tags producing at least one wrong match   203 of 370

    tag "agent"        matched 57 of 101 findings, 6 of which are about it
    tag "faq-agent"    matched 18,  4 about it
    tag "run"          matched 10,  1 about it

`agent` is not a contrived tag. It is the name segment of a real component in the corpus, and every
`agent:*` identifier in every repository contains it.

**A second hazard, latent rather than measured.** `tag.includes(component.split(':')[1] ?? '')` falls back
to the empty string, and every string contains the empty string, so a component identifier without a colon
would make every scenario match every finding. `ComponentId`'s pattern
(`packages/schema/src/identity.ts:42-46`) requires the colon, so the trap is closed today by a schema in
another package. It is recorded because the rule does not close it itself.

**Conclusion: no name matching survives.** Not narrowed, not thresholded. The corpus refutes it at both
scopes, and the honest replacement is not a better string test.

## The rule

> **A goal is judged against a recorded scenario result, and the scenarios its plan reruns are the ones
> whose recorded runs exercised the components the finding names. The baseline and the candidate are two
> executions of the same scenario under the same conditions, or there is no comparison and the goal says
> so.**

Two questions collapse into one because they were always one question. A comparison means something only
when both sides reproduce the same work; the plan decides what will be rerun; so the baseline has to be a
recording of that same thing, and the thing has to be one the store actually holds.

### What the store already knows, and what it needs

The join this product is built on is between what a repository declares and what a run exercised, and that
join is already persisted per run. `packages/usecases/src/audit.ts:189-197` writes
`saveComponentMetrics(runId, resolved)` for every run the audit reconciled, keyed by graph component
identifier. Measured on a clean demonstration store: after `audit`, `test --scenario support-desk`,
`audit`, every one of the three scenario runs carries 15 `component_metric` rows, one per component it
executed, every row with `execution_count >= 1`.

    agent:orchestrator                 1
    memory:conversation-memory         4
    model:demo-small                   4
    tool:lookup_account                1
    ...

The identifiers are the graph's own (`agent:orchestrator`, `tool:lookup_account`), the same namespace
`finding.components` uses. **So "which runs exercised the components this finding is about" is a question
the store can already answer from recorded execution, with no name in it.**

It answers it well. Asked for the six components of `independent-calls-run-sequentially` on the
demonstration store:

    scenario                fault plan             runs   components covered
    support-desk            (none)                 6      6 of 6
    support-desk-duplicate  fp_543e36f62ddab59f    3      6 of 6
    support-desk-faults     fp_5cab10f8c615cb56    3      3 of 6

`support-desk-faults` covers half, because the faults it injects stop the run before the rest execute.
That is the discrimination the tag rule never had, and it is measured rather than asserted.

Two facts make this cheap and one makes it need a migration.

- `run` is already indexed by `(scenario_id, started_at DESC)` and `scenario_result` by
  `(scenario_id, started_at DESC)` (`packages/persistence/src/migrations.ts:115,223`).
- `component_metric`'s primary key is `(run_id, component_id)`
  (`packages/persistence/src/migrations.ts:153-166`), so a lookup **by component** scans the table.
  **Migration 2 adds `CREATE INDEX component_metric_component ON component_metric(component_id)`.** It is
  forward only and appends, which is the rule the file states at `:1-10`.

### The selection, in order

Each step is a question the store answers, scoped, with a bound that is a ceiling on work rather than a
selection rule.

**1. Which runs exercised these components.** One query, not a window:

    SELECT r.id, r.scenario_id, r.variant_id, r.fault_plan_id, r.started_at
    FROM run r
    WHERE r.project_id = ? AND r.status = 'completed'
      AND EXISTS (SELECT 1 FROM component_metric cm
                  WHERE cm.run_id = r.id AND cm.component_id IN (...))
    ORDER BY r.started_at DESC, r.rowid DESC
    LIMIT ?

**2. Which scenarios those runs belong to.** The distinct `scenario_id` of the answer, newest first. A run
with no `scenario_id` exercised the components but belongs to no repeatable set, so it is not a validation
scenario: it stands for itself, which is settled, and the plan cannot rerun it.

**3. Which recorded result of each scenario could be a baseline.** The newest stored `ScenarioResult` for
that scenario. A `ScenarioResult` is the coherent unit already: one scenario, one environment, `repetitions`
with at least one member, an aggregate (`packages/schema/src/scenario-result.ts:72-89`). It is also the
unit `resolveSide` already resolves a named run to, through `repetitionSet`
(`packages/usecases/src/compare.ts:46-56`), so naming one of its runs on the compare command expands back
to the set with no new grammar.

**4. Its conditions, read rather than assumed.** Every repetition's `RunRecord` carries `variantId` and
`faultPlanId` (`packages/schema/src/run.ts:116-117`). A result whose repetitions disagree on either is not
one condition and is skipped. A result that agrees carries `(scenarioId, variantId, faultPlanId)`, which is
what the plan must reproduce.

**5. Whether it can supply samples.** A repetition run counts when it is `completed` and
`runMeasuredNothing` is false (`packages/domain/src/observation.ts:49-50`), which is the same test
`samplesFromRuns` applies, so the count the plan promises is the count the comparison will see. The
comparable result is the first, newest first, that supplies at least the sample floor.

**6. The pair.** That result's runs are `baselineRunIds`. Its scenario is the one the compare command's
candidate must be. Its conditions travel with the plan.

**Validation scenarios** are the scenarios from step 2, bounded, with the comparison's scenario ordered
**last**, so `latest` on the printed compare command resolves to the rerun of the scenario the baseline
came from. Every one of them still gets a `scenario_passes` criterion, because a scenario that exercised
the components is worth rerunning whether or not it is the one being compared.

### The sample floor is part of reachability, not a downstream surprise

`compareMetric` refuses a direction below three samples per side
(`packages/comparison/src/compare.ts:120-123`), and the demonstration system declares `repetitions: 1` for
two of its three scenarios. A selection rule cannot manufacture samples nobody recorded, so the floor is
asked **before** the criterion is written rather than discovered after the operator has run everything.

`comparisonIsReachable` (`packages/goals/src/create.ts`) becomes: a comparable pair exists, meaning a
recorded result the plan will rerun, under conditions the rerun reproduces. A second predicate,
`distributionIsDecidable`, adds the floor on both sides: the recorded result supplies at least
`MINIMUM_SAMPLES_PER_SIDE`, **and** the prescribed repetition count is at least that. The second half
matters: on the tree before this change, `orchescope goal create --repetitions 1` writes metric criteria
that the plan's own commands can never decide.

Splitting them is what keeps a one-repetition baseline honest without making it useless. Such a goal
states the criteria decided by presence, prescribes the comparison that decides them, and says in its own
document that the sample count is below what a direction needs, so the terms it does not state are
accounted for rather than absent.

The floor moves to `@orchescope/domain` as an exported constant and `compareMetric` takes it as its
default, because `goals` cannot import `comparison` under the layering AGENTS.md enforces, and two
independent threes are two numbers that can disagree.

### Conditions: required for selection, reported for everything else

The brief this design answers puts the choice plainly: either the rule requires the conditions to match,
or the goal states that they did not. **Both, at different layers, because they are different failures.**

- **Selection requires them.** The goal's baseline and its prescribed candidate are the same scenario, the
  same variant and the same fault plan. A comparison across conditions answers a question nobody asked, and
  the measurement above is what that costs: five regressions and three improvements, none of them about any
  change.
- **The comparison reports them.** `compareUseCase` knows both sides' runs. Where the two sides disagree on
  scenario, variant or fault plan, the comparison records it in `limitations`, which the schema already has
  (`packages/schema/src/comparison.ts:134`). This is not for the plan, which will not produce such a pair
  any more. It is for the hand-typed `orchescope compare A B`, which is a general tool and must stay one:
  refusing a deliberate cross-condition comparison would take away a real use, while saying nothing about
  it is what produced the defect at the top of this document.
- **The judgement will not bank one.** A `metric_improvement` or `metric_not_worse` criterion is decided
  only by a comparison whose two sides share the conditions the goal recorded. Otherwise it is undecided
  and says which condition differed. This is the layer that actually protects the verdict, because it is
  the only one an operator running commands by hand cannot route around.

That third layer is why the plan can rely on ordering for `latest` without that being a silent hazard. An
operator who reruns the scenarios in a different order produces a comparison whose candidate is a different
scenario; the comparison says so, and the criterion stays undecided rather than reporting a regression
nobody caused. **The honest fallback catches the ordering mistake**, which is what makes a new reference
grammar on `compare` unnecessary rather than merely unbuilt.

### Where there is no comparable pair

Which is a normal outcome, not a failure: a repository with no scenario, a repository whose only scenario
declares one repetition, a finding whose components nothing has exercised.

The metric criteria and the compare command are omitted, which is machinery `2a` already built, and
`comparisonNote` (`packages/goals/src/render.ts:48-54`) says which question failed:

- no run has exercised the components this finding names;
- the scenarios that exercised them have no stored result;
- the newest result of every such scenario supplies fewer than the floor, with the count it does supply;
- the plan's repetition count is below the floor.

Each of those is a different remedy and the current note cannot tell them apart, because it only knows
whether the two arrays were empty.

### The repository that has scenarios and has never run them

The rule's most visible consequence, and the one worth defending explicitly: with no runs recorded, no run
exercised anything, so the goal names **no** validation scenario at all. The rule it replaces named up to
three, because its fallback returned every scenario in the project.

That is the right answer and it costs nothing, because the goal document is not what tells an operator to
run a scenario. Measured on a copy of the demonstration system with its state cleared, holding three
scenarios and no runs: the goal for `model-call-without-timeout` carries only `finding_resolved` and says
"no recorded run has exercised the components this finding names", while the audit's own loop block, in the
same terminal document, ends

    missing         the same test, run again after the change
    run             orchescope test --scenario support-desk

`rerunStep` (`packages/report/src/loop-progress.ts:221-247`) reports the third step blocked with "written
down, none has ever run" and prescribes the command. So the loop advances from the bootstrap state through
the surface that is supposed to advance it, and the goal declines to name a scenario it has no evidence
about, which is the division of labour the rest of this design rests on.

A scenario that has never run is unknown rather than irrelevant, and running it is a remediation rather
than an acceptance criterion. Prescribing it inside the plan would name a command whose result decides
nothing, which is the failure the comment at `packages/goals/src/create.ts` argues against.

### What `baselineRunIds` means afterwards

Today the field carries three arbitrary recent runs and its schema comment says "Runs the candidate is
compared against" (`packages/schema/src/goal.ts:85-86`). After this it carries exactly that: the runs of
the comparable result, and nothing when there is no pair.

That is a real change for one guard. `createGoal` throws when
`finding.goalReadiness.requiresRuntimeEvidence` is true and `baselineRunIds` is empty
(`packages/goals/src/create.ts:346-354`), and its remediation is "Record a run with orchescope trace". Two
of the demonstration system's eligible findings set that flag (`retry-around-non-idempotent-operation`,
`duplicate-side-effect`), and both are runtime rules, so runs necessarily exist for them. The guard's
question is "does runtime evidence exist", not "is a comparison reachable", so it reads the runs from step 1
rather than the baseline: `CreateGoalInput` gains `exercisingRunIds`, the guard reads that, and
`baselineRunIds` keeps meaning what it says. Two meanings in one field is how the present defect reads to
anyone auditing it.

## What this refuses to do

- **Any name list, and any substring test between identifiers.** Measured above: 20.4 per cent wrong within
  a repository, 63.6 per cent across the corpus vocabulary, under the assumption most favourable to the
  rule. [ADR 0015](../architecture/adr/0015-the-asymmetric-invariant.md) records what a name costs on the
  runtime half, and this is the runtime half.
- **A bigger window.** `limit: 20` is not raised. The defect is that the question is unscoped, and the
  scoped question is a `WHERE` clause the store can answer with an index.
- **Padding or reusing samples.** A run appears on one side or neither. A one-repetition result supplies one
  sample and is reported as supplying one; it does not become a baseline and the plan says why.
- **Tuning until the demo passes.** The demonstration system has three scenarios and one project, and it
  cannot tell anyone whether a rule scales. What the demo is used for here is the end-to-end falsifier,
  where it is the only system in the tree that has scenarios at all. The scaling evidence is the corpus
  measurement, which is what refuted the rule being replaced.

## Falsifiers

Each is run against the tree at `7678100` and shown failing, then against the new tree and shown passing.
Anything that passes both ways is labelled a guard and is not counted as a falsifier.

- **F1, the cross-condition comparison.** A store holding a result of scenario A with no fault plan and a
  newer result of scenario B under one. A goal cut from a finding whose components both exercised must not
  prescribe a comparison whose two sides are A and B. **Old tree: prescribes exactly that**, which is the
  measurement at the top of this document.
- **F2, selection is by execution and not by tags.** Two scenarios, one exercising the finding's components
  and carrying no tag in common with it, one exercising nothing of them and carrying every tag it has. The
  plan must name the first. **Old tree: names both**, in tag order, because the tag rule matches the second
  and the fallback returns everything.
- **F3, the floor is asked before the criterion is written.** A finding whose only exercising scenario has a
  single recorded repetition must produce a goal stating no criterion about a distribution, keeping the one
  decided by presence, and saying in its own document that the baseline is below the floor. **Old tree:
  writes `successRate` and `durationMs.p95`** and prescribes a compare that comes back indeterminate for
  both.
- **F4, the comparison reports differing conditions.** `orchescope compare` across two scenarios records a
  limitation naming the difference. **Old tree: records nothing**, which is the ten deltas above.
- **F5, the judgement will not bank a cross-condition metric.** A goal whose stored comparison compares two
  different scenarios leaves its metric criteria undecided with the reason, rather than reporting them
  satisfied or regressed. **Old tree: decides them.**
- **F6, the loop still closes.** The end-to-end improvement-loop test runs the plan verbatim and the goal
  reaches its criteria on a comparison of one scenario against itself. A **guard** on the machinery
  `F5` of the closing-the-loop design built, not a falsifier.
- **F7, a run no scenario repeated is not given a set.** Settled already; a **guard** that this rule does
  not reintroduce one by treating an exercising trace run as a baseline.

## Corpus impact, stated in advance

None expected, and no rebaseline will be asked for without the entry, the before, the after and the reason,
per entry.

Nothing here touches a discovery reader, an adapter, a matcher or a rule. It changes which runs a goal
names and what a comparison records about its own sides. The corpus measures discovery against pinned
repositories and holds no goal and no comparison: `corpus/expected/*.json` carries `adapters`,
`components`, `findings`, `relations`, `files`, `languagesNotAnalysed` and nothing about the loop. The 48
matched expectations, the 1588 semantic assertions, the 88 injected shapes and the 87 recognition names
should all be unmoved. **If any of them moves, that is a defect in this design and not a number to
re-record.**

## Sequencing, as separable commits, each with its own gate

    1. Index the component metric by the component it names.                    migration 2
    2. Ask which runs exercised a set of components.                            store query
    3. Choose a goal's baseline and its scenarios from one recorded result.     F1, F2, F3
    4. Say what a comparison could not compare.                                 F4
    5. Refuse to decide a metric criterion across conditions.                   F5

Commit 1 and 2 are inert on their own and are checked in isolation before the split is relied on, which is
the trap two commits in the previous range fell into.

## What this design does not fix

- **A repository with no scenario still gets no comparison.** The rule makes that explicit and says why; it
  does not create a scenario. That is item 3 of
  [the closing-the-loop design](0.9.4-closing-the-loop-design.md), still untouched.
- **A run that no audit has reconciled has no component metrics**, so it cannot be selected by execution.
  The metrics are written by the audit (`packages/usecases/src/audit.ts:189-197`) over the newest
  `--runs` runs, which defaults to 10 and is capped at 100 (`audit.ts:70-82`). Two consequences, measured
  rather than assumed. Coverage **accumulates**, because `saveComponentMetrics` replaces only the run it is
  given (`packages/persistence/src/repositories/runs.ts:256-261`), so the rule reads every run any audit
  ever reconciled rather than a window; that is strictly more history than the twenty-run scan it replaces,
  and it is filtered to relevance where that one was not. But a run recorded **after** the last audit is
  invisible to step 1 until the next one. The plan's first command is `orchescope audit`, which is what
  makes this self-correcting inside the loop; a goal cut immediately after a run and before an audit sees
  less than the store holds. Recorded, not fixed: writing metrics at run time would mean inventing
  component identities before a graph exists, which `packages/scenarios/src/run.ts:134-137` refuses on
  purpose.
- **A baseline older than the window is not reachable.** The exercising query returns the newest runs that
  touched the components, bounded, and coverage ranks among those rather than past them. That bound is
  deliberate and is about staleness rather than work: a recording covering everything the finding names but
  predating a year of unrelated change is not the better baseline, because the candidate is a fresh rerun
  and every one of those changes lands in the difference. What it costs is a repository whose only
  well-covering scenario has not run in a long time, which gets a narrower baseline or none. Bounding by
  time rather than by run count would state that intent more directly and is not built.

- **`metric_improvement` end to end on a real third-party repository** stays unverified. This work makes it
  reachable in principle by giving it a comparable pair; whether any of the three rules that can produce one
  ever does on a repository nobody here wrote is still the falsifier worth having.
- **The environment is not part of the conditions.** `RunEnvironment` records the platform, the cpu count
  and a load average (`packages/schema/src/run.ts:36-51`), and a baseline recorded on a loaded machine is
  weaker evidence than one recorded on an idle one. The comparison already says something about sample size
  and says nothing about this. Out of scope and named.
- **Nothing here re-opens what is settled**: the metrics a criterion names stay scoped to that goal's
  comparison, a quantile stays gated on the floor rather than on the means, a traced run stays standing for
  itself, `manual_review` stays an attestation, and a skipped evaluator stays not a pass.
