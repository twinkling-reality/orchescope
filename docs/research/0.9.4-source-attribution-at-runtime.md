# Source attribution at runtime, scoped

A scope, not a design. It names the one change that would make the declared-against-exercised join stop
depending on a catalogue of framework names, states what is already built, what is missing, what has to be
measured before any of it is written, and what would make it not worth doing.

[ADR 0015](../architecture/adr/0015-the-asymmetric-invariant.md) is the record this answers. Its decision 4
names this work and deliberately does not decide it.

## The problem, in one paragraph

Reconciliation joins the two halves of the product by four rules, strongest first
(`packages/graph/src/reconcile.ts:41-47`): a shared code location, a runtime name a manifest declared, a
kind and a name, and a bare name the runtime qualified. Three of the four are name matches, and the names
come from the declared half, which is a catalogue of framework readers that decays. Measured over the
pinned corpus, that catalogue was already wrong about the frameworks it does cover: the symbol `Server` and
the methods `setRequestHandler` and `add_tool` matched nothing across fifty six repositories, and neither
did any of the eight entries of the language table.

The first rule does not have that problem. A code location is produced by the run and read off the source,
and neither end needs anybody to have written a reader for the framework in between.

## Read this first

**All four measurements are done and they narrow this proposal substantially.**
[Cost](0.9.4-stack-capture-cost.md) and [reach](0.9.4-repository-frame-depth.md) came back affordable.
[What it actually buys](0.9.4-what-source-attribution-actually-buys.md) came back much smaller: on a built
application the frame names the build output and no corpus application ships a runtime source map, and a
framework that streams puts no repository frame on the stack at all. That document also corrects the
premise below: the producing half is not missing, it is unshipped in `corpus/instrumentation/`. Read it
before acting on anything here.

## What is already built, which is more than I expected

The consuming half exists and is complete.

- `packages/traces/src/attributes.ts:53-58` reads `code.file.path`, `code.function.name`,
  `code.line.number` and the two legacy spellings.
- `packages/traces/src/source-identity.ts` turns them into an `ObservedCodeLocation`, records
  `codeLocationProvenance` for each part, and refuses rather than guesses where a part is missing.
- `orchescope.code.repository.path` (`attributes.ts:94`) is the repository-relative form, and
  `repositoryPath` (`source-identity.ts:74`) normalises it.
- `reconcile.ts:450-456` already builds a component's `sourceLocations` from `observed.codeLocation`, and
  `code_location` is already the strongest match rule.

The producing half does not exist. **Nothing in `packages/instrumentation/` writes any of those
attributes.** `instrumentedFetch` (`outbound-fetch.ts`) writes `http.*`, `gen_ai.*`, `mcp.*` and
`orchescope.component`, and no `code.*`. The only place in the repository that writes them is
`apps/demo/src/telemetry.ts:41-43`, which is the fixture, by hand.

So the work is not "build a join keyed on location". The join is built and it has no producer.

## What the change is

The shim captures the source location of the call that reached it, and puts it on the span it was already
going to emit.

The frame that matters is **the deepest frame inside the repository under audit**. A `fetch` inside an SDK
is called from the SDK, which is called from the framework, which is called from the repository's own file,
and only the last of those is a location a declaration could ever have been read from. That is a rule about
paths and not about names, and `repositoryPath` already exists to apply it.

## What has to be measured before any of it is written

Four questions, and the work should not start until three of them have numbers.

**1. What does a stack capture cost, per request, on both runtimes? ANSWERED, and it is affordable.**
[The measurement](0.9.4-stack-capture-cost.md) has the numbers. A five frame capture costs 3,250 nanoseconds
on Node and 486 on Python, which is 2.35 per cent and 0.28 per cent of one loopback HTTP request, against a
shim that already costs 18.3 per cent of one. The cost tracks the bound and not the stack, measured flat
across depths from 5 to 200, so a prohibition on unbounded work is satisfiable here rather than merely
intended. Twenty eight bytes allocated per capture and nothing retained, which holds only because the rule
drops the frames rather than storing them. A fifty frame bound costs about what the shim already costs, so
the bound can be chosen on whether it reaches a repository frame rather than on price.

Two constraints came out of it. `inspect.stack()` scales with depth and reaches 1.52 milliseconds at depth
200, nine times a whole loopback request, so the `f_back` walk is the only affordable form in Python. And
`Error.stackTraceLimit` and `Error.prepareStackTrace` are process-wide and must both be saved and restored
synchronously, or the shim truncates and reshapes every stack the target itself takes.

**2. How often is the deepest repository frame the right one, on real repositories? ANSWERED for Node,
answered with a caveat for Python.** [The measurement](0.9.4-repository-frame-depth.md) has the numbers. A
twenty frame bound reaches the repository's own file through all four Node stacks measured, including
`ai` over `@ai-sdk/openai` and `@openai/agents`, where the framework's own machinery is about a dozen
frames deep. Python reaches it at ten. Two findings came out of it that were not in this list: a repository
function written `return call(...)` rather than `return await call(...)` has no frame on the stack at any
bound, and **Python has no platform global to patch at all**, so a Python shim inherits the catalogue
problem this whole effort exists to remove. The second is serious enough to reopen the Python half of this
scope.

**3. What does the location look like after bundling, transpiling and a source map? ANSWERED, and it is the
blocker.** `getFileName()` returns the build output in all seven configurations tested, and 0 of the 11
built packages in the corpus that hold a model call ask for a runtime source map. Original text follows.** A repository shipping
transpiled TypeScript reports a location in `dist/`, which no declaration was read from. Node's
`--enable-source-maps` and the `sourceMapsEnabled` flag exist; whether the shim can rely on them without
requiring the target to opt in is unmeasured. This is the question most likely to make the change smaller
than it sounds.

**4. What happens where the deepest repository frame is a framework vendored into the repository? ANSWERED:
the application's own frame is strictly interior and both endpoint rules name the wrong file. Rare in this
corpus. Streaming, measured alongside it, is the worse finding: zero repository frames at any bound.
Original text follows.** A
monorepo that vendors its own agent framework has repository frames all the way down, and the deepest one
is the framework's, not the caller's. This one can be answered after the others.

## What it would buy, stated as a claim that can be checked

**A framework nobody has written a reader for produces a correct join.** Today, a repository built on such
a framework produces a static graph with no agent in it and a runtime topology with spans that join to
nothing, and the delta is empty because both halves are empty. With a location on the span, the run says
"a model was called from `src/orchestrator.py:88`", and that is a component with an identity, a source
location a reader can open, and an exercise record. The catalogue is not consulted.

**The falsifier is exactly that sentence.** Take a repository using a framework `DEFAULT_ADAPTERS` does not
claim, trace it, and require the report to name the file and line its model calls were made from. It fails
today. If it still fails after the change, the change did not work.

## What it does not buy, so the scope is honest

- **Nothing for a repository that is never run.** The audit half stays a catalogue and stays the only thing
  an unrun repository has. This raises the value of tracing; it does not lower the value of the catalogue.
- **Nothing for a call the shim cannot see.** The shim patches `fetch`. A model called over a socket, a gRPC
  channel or a vendored HTTP client is invisible to it, with or without a location.
- **No component name.** A location says where, not what. `entrypoint:orchestrator` is a name the enclosing
  function supplies; the kind of component it is remains an inference, and an honest one is `entrypoint`
  rather than `agent`, which is what [ADR 0014](../architecture/adr/0014-layer-three-refusal-and-the-model-call-frame.md)
  already decided for the static side of the same question.
- **It does not remove a single framework adapter.** Depth stays depth. What changes is that depth stops
  being the only thing that produces a join.

## The one sentence ADR 0014 will have to be amended on

> The frame is not observable. It stays out of `OBSERVABLE_KINDS`. Auto-instrumentation observes HTTP
> requests, never function names, so a source-only enclosing-function identity can never appear in a span.

That is true of the shim as built and it is not true of the platforms it runs on. If measurement 1 says a
bounded capture is affordable, the second sentence stops being true and the decision that rests on it has to
be made again on the new evidence. ADR 0015 records this in advance so that the amendment is expected rather
than discovered.

## Sequencing, if it goes ahead

1. The four measurements above, written up with numbers, before any shim change. **Two of four are done.**
   Cost is settled and reach is settled for Node. What remains is source maps, vendored frameworks, and the
   question measurement 2 added: what a Python shim would patch, given there is no `fetch` there.
2. The capture, bounded, behind a setting that defaults off, with the cost measured on the demonstration
   system and on the three traced corpus entries.
3. The repository-frame rule, measured against question 2's rate.
4. The default flipped on, only once the cost is a number in a document.
5. `OBSERVABLE_KINDS` and ADR 0014's frame decision revisited, on the evidence, as a separate record.

## What would make this not worth doing

**A stack capture that costs enough to change a run.** Measured and answered: it does not. That reversal
condition is closed, and the remaining two are the ones to watch.

**A repository frame that is usually the wrong file.** Measurement 2 shows the frame is reachable and is the
right file on unbundled source. Bundling and vendoring are still open, and they are now the whole of this
condition rather than most of it.

**Python having no transport a shim can rely on.** Measurement 2 found that `openai` 3.3.1 sends through
`httpx2` rather than `httpx`, a different distribution the same vendor moved to between majors. If a Python
shim's transport list is a catalogue that decays, the Python half of this proposal reproduces the defect it
was meant to remove, and should be dropped rather than shipped with a list.

**Nobody tracing anything.** The instrumentation package's own header records that "two independent sessions
across thirty seven runs of real systems collected zero spans between them". If that is still true, the
half of the product that scales is the half nobody runs, and the honest conclusion is that the product's
value is the audit and the audit is a catalogue. That would be a finding about the product rather than about
this change, and it is the one worth knowing first.
