# What source attribution actually buys, measured

Measurements 3 and 4 of [the scope](0.9.4-source-attribution-at-runtime.md), plus the frequency question
[measurement 2](0.9.4-repository-frame-depth.md) left open, plus a correction to the scope's own premise.

**The proposal is narrower than the scope claims.** Measurements 1 and 2 said a bounded capture is cheap and
reaches the repository's own file. Measurements 3 and 4 say it reaches a file that exists on disk in the
build output rather than the file a declaration was read from, on every built application in the corpus, and
that it reaches nothing at all when a framework streams. The hazard the scope worried about most, the tail
return, turns out not to exist.

## The correction: the producing half is not missing, it is unshipped

The scope says "the producing half does not exist" and cites `packages/instrumentation/`. That is true of
that directory and false of the repository. **`corpus/instrumentation/` holds four source-identity
producers** already: `node_source_identity.mjs` (172 lines, `getCallSites` from `node:util`, `MAX_FRAMES` of
64, writing `code.file.path`), `crewai_source_identity.py`, `mcp_stdio_source_identity.mjs` and
`openai_agents_mcp_source_identity.mjs`.

They are how the corpus produces its only code-location joins, and `scripts/package.mjs` stages none of
them. So the work is not "build a capture". It is **promote a prototype that already exists into the shipped
shim**, which is a smaller job than the scope describes and a different one.

`getCallSites` priced beside the `Error.captureStackTrace` figures in
[measurement 1](0.9.4-stack-capture-cost.md), nanoseconds, p50:

| depth | limit 5 | limit 20 | limit 50 | limit 64 |
| --- | --- | --- | --- | --- |
| 20 | 4,497 | 13,548 | 18,301 | 18,342 |
| 50 | 4,295 | 13,777 | 31,989 | 38,123 |
| 200 | 4,537 | 16,346 | 37,960 | 46,634 |

It is about 1.5 times `Error.captureStackTrace` at the same bound, and unlike it the cost is **not** flat in
depth past a bound of 20. The prototype's 64 frame bound costs 46,634 nanoseconds at depth 200, which is
34 per cent of an instrumented loopback request. Its `{ sourceMap: true }` option costs a further 30 per
cent, 21,655 against 16,659 at limit 20.

## The tail return does not matter

Measured over all 56 entries, JavaScript and TypeScript, first-party non-test source, 3,911 modules read and
verified byte for byte against their recorded content hash, 121,063 call facts.

`CallFact.awaited` (`packages/source-analysis/src/facts.ts:134`) is the exact discriminator and it is
populated by the JavaScript analyzer. A lexical read of the source agreed with it on **9,203 of 9,203
sites, zero disagreements.**

**Of 823 model-call sites, 786 (95.5 per cent) are awaited by the repository's own function, and 0 are in a
bare tail-return position.** The repository's own layers between an entry point and a model call are one to
three deep, mode zero, maximum three, and 78.8 per cent of first-party edges into an async callable are
awaited. The hazard is real in the language and absent from the code.

One gap found on the way: **`DefinitionFact.returns` is never populated for JavaScript or TypeScript.**
`returnsOf` exists only in `packages/source-analysis/src/python/analyze.ts:1498-1533`. Anything asking "what
does this function return" gets nothing in half the corpus.

## Measurement 3: on a built application the frame names the build output

Seven source-map configurations, six deployment shapes, real installs of `typescript` 5.9.3, `esbuild`
0.28.2, `source-map-support` 0.5.21 and `next` 15.5.24.

**`CallSite.getFileName()` returned the build output and never the authored file, in all seven
configurations and all six shapes.** The rule as the scope specifies it, `getFileName` plus `getLineNumber`,
never names a file a declaration was read from on any built repository.

`node:module`'s `findSourceMap().findOrigin()` recovers the authored file exactly, at about three per cent
over the capture. That is affordable. **It is also unusable, because there is no map to resolve against:
across the 56 entries there are 11 built packages holding a JavaScript or TypeScript model call and zero of
them ask for a runtime source map.** The 105 tsconfigs that do set `sourceMap` belong to three library
repositories publishing to npm, none of them the process making the call.

Six of the eleven are Next.js applications, which is the shape most real agent applications in this corpus
take.

## Measurement 4: streaming loses the frame entirely, vendoring puts it in the middle

**Streaming through a framework puts zero repository frames on the stack, at any bound.** Three of eight
Node cases measured, `ai`'s `streamText` in both spellings and `@openai/agents` with `stream: true`, reach
the patched `fetch` from the framework's own stream scheduler. The same frameworks non-streamed put the
repository frame at index 16 and 13. **This is worse than the tail return, because the tail return is a way
the caller wrote a line and this is not avoidable by any spelling the caller can choose.**

**Vendoring breaks both endpoint rules.** With a framework copied inside the repository, the application's
own file is strictly interior: four framework frames below it, the entry point above it, all six under the
repository root. Neither "nearest to the transport" nor "furthest from it" names the caller. It is rare in
this corpus, which is the only thing that saves it.

Retries are not a defect. A forced second attempt still carries the repository frame.

## What survives

The location rule holds for a Node repository that is **not built, not streaming and not vendoring its
framework**. That is a real population and it is not the dominant one. Every Next.js application in the
corpus fails the first condition, and streaming is the default shape of a chat application.

## What this changes

**The scope's reversal condition "a repository frame that is usually the wrong file" is met**, for built
applications, which is most of them. The condition should be read as triggered rather than open.

**The change is still worth making and it is worth less than claimed.** It would move joins from
`kind_and_name` to `code_location` for unbuilt, non-streaming Node targets, and do nothing for the rest.
Whoever picks it up should read this document before the scope, and should start by promoting
`corpus/instrumentation/node_source_identity.mjs` rather than by writing a capture.

**Two questions this raises that nobody has asked yet.** Whether a build step could be asked to emit a
source map, which turns measurement 3 from a blocker into a setup instruction. And whether the streaming
path can be reached at all, since a scheduler frame is not a caller frame under any rule over stacks.
