# Used 0.9.2 acceptance holdouts

An independent post-publication acceptance check of the published `orchescope@0.9.2`, run before the
release was showcased. It follows the [pre-release blind evaluation protocol](../guides/pre-release-blind-evaluation.md)
and extends it: eight targets rather than one pair, and a deliberate bias toward repositories that could
be **run** rather than only scanned, because the declared against exercised join is the product's central
claim and its least measured surface.

This record preserves the eight repositories used. **They are regression inputs, not unseen holdouts, at
any later revision.** Do not select any of them, any owner lineage, or a fork of any of their trees as a
blind holdout for 0.9.3 or later.

No Orchescope source was changed during or after measurement. Nothing here is fixed; this is the report
the 0.9.3 decision is made from.

default branch, push date, fork status) via the GitHub repositories API, and was written down in full

`schemas/`, and the complete reachable Git history (`git log --all -S`, `git log --all --grep`, and a blob
search across `git rev-list --all`). Zero occurrences of any selected owner, repository name, URL, commit
or tree.

**One disclosure.** [`competitive-boundary.md:13`](competitive-boundary.md) names "Mastra Studio" in a
table of competing *products*. That is a market reference to `mastra-ai`'s own studio UI: not a repository
lineage, not a URL, not a revision, not a corpus pin, and it carries no expected answer. The selected
target `laoposkj/mastra-agentic-rag` is an unrelated third-party application, absent everywhere. Recorded
so the release owner weighs it rather than discovers it.

## False positives

| # | Claim | Location | What the source says |
|---|---|---|---|
| A | `agent:embedtext`, `inferredFrom: 'single generation call'` | `T2 src/mastra/rag/embeddings.ts:13` | a three-line embedding helper; `embed()` is not a generation call and the function has no instructions, tools or loop |
| B | `model:embedding/unspecified`, no provider component | `T2 src/mastra/rag/embeddings.ts:15` | provider is `@ai-sdk/openai` via `createOpenAI` at lines 1 and 10; `embedding` is the SDK method name, not a provider. The model is the literal `'text-embedding-3-small'` at `constants.ts:5` |
| C | `agentSystemDetected: true` | T2 | rests entirely on A and B. The repository's real agent was refused, so the headline claim is carried by the two components that are wrong |
| D | seven `agent:` components | `T6 examples/02_openai-intro/openai-intro.js:15,32,50,77,116,139,161` | seven demo functions, one bare `chat.completions.create` each, no tools, no loop |

A, C and D share one cause. Both `packages/discovery/src/adapters/vercel-ai-sdk.ts` and the model SDK
adapter mint a component of `kind: 'agent'` for the function enclosing any generation call. The
vercel-ai-sdk adapter's header draws the right distinction and the code does not carry it into the
component kind: it says a call passing a tools map "is a tool using loop and is modelled as an agent,
while a bare text generation is modelled as a model call attributed to its enclosing function", and warns
that "overstating a one shot completion as an agent system would make the graph look busier than the code
is". In the code both branches add `kind: 'agent'`; only `confidence` and `role` differ. `embed` is also
in that adapter's `GENERATION_CALLS` list, so an embedding call mints an agent too. Because `model` and
`agent` are both in `AGENT_SYSTEM_KINDS` (`packages/domain/src/audited-system.ts:11`), a repository whose
only AI usage is one `embed()` call is reported as a detected agent system.

## Runtime join measurement

Three targets were run, not just scanned. All runs used a local Ollama; no provider credential was used
and no provider was reached. Every run was driven through the repository's own classes and entry points;
no target source was modified.

### T5: the join working

`orchescope trace -- node driver.mjs`, `run_cb48661e9d28252d`, 3 spans, exit 0. The run connected a real
`@modelcontextprotocol/server-filesystem` over stdio, listed 14 tools, and executed one real `tools/call`
for `list_directory`.

The MCP stdio patch fired on genuinely third-party code and recorded `tool:list_directory` by the name
reconciliation joins on. `exercised-not-declared` fired correctly at high severity. This is the product's
central mechanism working on a repository nobody involved had seen.

Two problems in the same run. The two Ollama chat completions were recorded as
`external_service:localhost-11434` with `sideEffects: 2` and `modelCalls: 0`. The runtime guide states
that a model call is deliberately *not* recorded as an outside effect, precisely so that "two chat
completions in one run" are not reported as effects, and that invariant holds only for hosts in
`BY_HOST_SUFFIX`. And `topology-shape` reported `clear | 2 declared components examined` when both
components were runtime-only and the declared population was zero.

### T6: the join producing a false claim

`orchescope trace -- node examples/02_openai-intro/openai-intro.js`, `run_fd3dff521a413ddc`, 10 spans,
exit 0, against a local Ollama serving models aliased `gpt-4o` and `gpt-3.5-turbo`. The command's own
output shows all seven examples executing and both models answering; eight chat completions were made.

Orchescope then reported, from that run:

- `declared-not-exercised` (low): **"9 declared components were never exercised by a recorded run … The
  agent agent:basiccompletion was discovered in the repository and did not appear in any of the 1
  recorded run. Either no scenario reaches it, or it is unreachable in practice."**
- `observability-coverage` (medium): **"Only 0 percent of declared components were exercised. 0 of 9
  declared components appeared in a run."**

The nine components named are the seven agents and both models, every one of which came from the exact
file the traced command ran, and every one of which executed. Both disjuncts of "either no scenario
reaches it, or it is unreachable in practice" are false. `modelCalls: 0`, `sideEffects: 10`.

The mechanical cause is the host table: `127.0.0.1:11434` is not a recognised provider host, so no model
span exists to join against. But the consequence is not a bounded refusal. **It is an affirmative,
actionable, wrong claim about the repository**, and the protocol draws exactly that line: an honest
refusal is an evidence boundary; turning a refusal into a positive claim is not.

There is a second, independent half to this. The seven `agent:` components are minted by Orchescope from
bare completion calls, and Orchescope's own auto-instrumentation observes HTTP requests, not function
names. No span can ever carry those identities. Components the product invents that its own runtime half
can never observe will report `declared-not-exercised` on every run forever, including against a
recognised provider host.

## What this says about the central claim

The declared against exercised join is the differentiator. On the three targets where it was actually
exercised on unseen third-party code:

- it **worked** once, on the MCP tool-name join (T5);
- it **inverted** once, reporting a declared agent as undeclared because the static half could not read
  the declaration (T1);
- it **produced a false negative claim** once, reporting nine exercised components as never exercised
  because the runtime half could not name a self-hosted model endpoint (T6).

Both failures are joins between two halves that disagree, and in both the product resolved the
disagreement by asserting rather than by refusing. That is the pattern worth fixing in 0.9.3, and it is
more consequential than any individual missing adapter.
