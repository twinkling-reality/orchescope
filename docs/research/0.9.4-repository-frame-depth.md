# How far the repository's own frame is from the transport

Measurement 2 of the four [the source attribution scope](0.9.4-source-attribution-at-runtime.md) names, and
the one that decides whether the change is useful rather than whether it is possible.
[Measurement 1](0.9.4-stack-capture-cost.md) priced the capture; this one asks whether a capture of that
size reaches anything worth having.

**Answer: a twenty frame bound reaches the repository's own file through every SDK and framework measured,
and it costs about seven per cent of the fastest request that can exist.** Two findings came out of the
measurement that were not in the design, and one of them is worse than the answer is good.

Measured against real distributions installed for the purpose, against a local mock that answers the two
response shapes these SDKs ask for. Versions: `openai` 7.5.0, `ai` 7.0.79, `@ai-sdk/openai` 4.0.47,
`@openai/agents` 0.17.0 on `node v24.15.0`; `openai` 3.3.1 and `httpx2` 2.12.0 on `python 3.14.6`.
Scripts under `scratchpad/depth/`.

The application under audit is a `src/` directory and nothing else. The harness that starts the mock,
patches the transport and classifies frames sits outside it, so a frame belonging to the measurement can
never be counted as a frame belonging to the repository. An earlier version of this measurement did count
one, and reported a reach it did not have.

## Node: how deep the repository frame is

Index 0 is the frame that called the patched `fetch`.

| stack | frames | repository frame at | limit 5 | limit 10 | limit 20 | limit 50 |
| --- | --- | --- | --- | --- | --- | --- |
| `openai` SDK, one own layer | 6 | 4 | yes | yes | yes | yes |
| `openai` SDK, two own layers | 8 | 6 | no | yes | yes | yes |
| `ai` over `@ai-sdk/openai` | 18 | 16 | no | no | **yes** | yes |
| `@openai/agents` over `openai` | 15 | 13 | no | no | **yes** | yes |

The composition is the readable part. Through the bare SDK the shape is three dependency frames, the async
boundary, then the repository. Through a framework it is three dependency frames, the async boundary, then
twelve more dependency frames, then the repository. **The framework's own machinery is what a bound has to
be large enough to cross, and it is about a dozen frames.**

**Limit 5 reaches one of four. Limit 10 reaches two. Limit 20 reaches all four.** Against measurement 1, a
twenty frame bound costs 9,256 to 9,751 nanoseconds, which is seven per cent of an instrumented loopback
request and a ten-thousandth of a real provider call. That is the recommendation, and it is chosen on reach
rather than on price because price stopped being the constraint.

## Python: shallower, and it reaches sooner

| stack | frames | repository frame at | limit 5 | limit 10 | limit 20 |
| --- | --- | --- | --- | --- | --- |
| `openai` SDK sync, one own layer | 10 | 7 | no | yes | yes |
| `openai` SDK sync, two own layers | 12 | 7 | no | yes | yes |
| `openai` SDK async, one own layer | 16 | 6 | no | yes | yes |
| `openai` SDK async, two own layers | 18 | 6 | no | yes | yes |

**A `f_back` walk crosses `await` without losing anything.** In the asynchronous cases the repository frame
sits at index 6, the asyncio event loop's own frames follow it, and the repository's outer frame appears
again below them. A coroutine suspended at an await keeps its frame in the chain, so Python has no
equivalent of the hazard below. **Limit 10 reaches all four**, at 899 nanoseconds.

## The first finding: a tail return removes the frame, at any bound

Isolated with the same call written five ways the language allows, through the same SDK.

| how the repository's own function is written | frames | repository frame at |
| --- | --- | --- |
| `return call(...)` | 5 | **none on the stack** |
| `return await call(...)` | 6 | 4 |
| `const answer = await call(...); return answer` | 6 | 4 |
| two own layers, both awaiting | 7 | 5 |
| inner tail returns, outer awaits | 6 | 4 |

V8 keeps the frame of a function that is *suspended at an await*. A function that returns a promise without
awaiting it has already returned by the time that promise settles, so there is no frame to keep and no bound
recovers one. **The distinction is invisible in the source and it decides whether the repository appears at
all.**

It is survivable rather than fatal, and the last row is why: one `await` anywhere in the repository's own
chain restores a frame. A repository whose every layer tail-returns is invisible to this rule, and how
common that is across real repositories is not measured here.

## The second finding: Python has no `fetch`, and the transport already moved

The Node shim patches `fetch`, a platform global no SDK can avoid. **Python has no equivalent, and the
measurement found that out the hard way: nothing fired.**

`openai` 3.3.1 does not send through `httpx`. It sends through **`httpx2`**, a different distribution at a
different version, declared in its own metadata as `Requires-Dist: httpx2<3,>=2.7.0`, with its own `Client`
class that is not `httpx.Client`. The same vendor changed HTTP library between major versions and ships a
migration guide for it.

A Python shim therefore has to patch whatever each SDK happened to choose, and that list is a catalogue of
transport names that decays exactly the way [ADR 0015](../architecture/adr/0015-the-asymmetric-invariant.md)
says a catalogue decays. **It has already decayed once, visibly, inside the single most common SDK in this
domain.** The asymmetry that record states, that the runtime half is the framework-blind half, is true of
Node because of `fetch` and is not established for Python at all.

That is the most important sentence in this document and it was not in the scope's four questions.

## What this changes about the scope

**Measurement 2 is answered for Node and answered with a caveat for Python.** The bound is twenty; it
reaches every framework measured; it costs seven per cent of the fastest possible request.

**The Python half of the proposal now needs a question the scope did not ask:** what does a Python shim
patch, and what does that list cost to maintain. Until that has an answer, source attribution is a Node
feature with a Python aspiration, and it should be described that way.

## What this does not answer

**Source maps.** Every measurement here ran on unbundled ESM, so the file the frame reports is the file the
author wrote. A transpiled repository reports its build output, and overriding `prepareStackTrace` during
the capture means the target's own source-map hook is not consulted. That is measurement 3 and it is
untouched.

**Vendored frameworks.** A monorepo that vendors its agent framework has repository frames all the way down,
and the deepest is the framework's rather than the caller's. That is measurement 4 and it is untouched.

**How often real repositories tail-return.** The hazard is isolated and its blast radius is unmeasured. It
is measurable against the corpus and was not measured here.

**Streaming.** Every case measured is a single non-streamed completion. A streamed response may reach the
transport from a different place in the SDK, and that is not measured.
